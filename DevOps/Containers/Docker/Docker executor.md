**Docker executor** — это термин, который обычно применяется в контексте систем автоматизации сборки и CI/CD (Continuous Integration / Continuous Delivery), например, в GitLab CI, Jenkins, TeamCity, Drone, CircleCI и других. Он означает способ выполнения билдов и тестов в изолированных Docker-контейнерах.
  
### Кратко: что такое Docker executor?

*Docker executor* (или Docker runner/executor) — это компонент, который запускает ваши CI-задания внутри Docker-контейнера. Вместо выполнения сборки на "голой" виртуальной или физической машине, runner изолирует задачу в контейнере, создавая контролируемое окружение с нужной версией языка, библиотек и утилит.

#### Примеры

- **GitLab CI**: один из режимов раннера — docker executor.
- **Jenkins**: с помощью Docker Plugin можно запускать каждый build step в отдельном контейнере.
- **Drone, CircleCI**: по сути каждый job запускается в отдельном контейнере.

---

## Плюсы Docker executor

**1. Изоляция окружения**
- Контейнер предоставляет полностью отдельное ПО; зависимости сборки не пересекаются между задачами.
- Исключает "эффект соседа" и делает сборки повторяемыми.

**2. Чистота и предсказуемость**
- Каждый раз можно стартовать с нового, гарантированно чистого образа. Нет "мусора" или неожиданных артефактов прошлых сборок.

**3. Лёгкая смена окружения**
- Можно легко билдить проекты для разных платформ, версий инструментов, языков.
- Просто используешь разные базовые образы.

**4. Безопасность**
- Разграничение между build-job’ами.
- Меньше шансов «заразить» CI-сервер вредоносным кодом.

**5. Масштабируемость**
- Удобно масштабировать — в том числе в Kubernetes/в облаке.

---  
## Минусы и ограничения Docker executor

**1. Дополнительная сложность**
- Нужно хорошо понимать, как работают Docker-контейнеры и как их настраивать (volumes, сети, права, безопасность).
- Иногда требует доработки пайплайна (например, не все команды можно выполнить в контейнере так же, как на host’е).

**2. Проблемы с доступом к "железу"**
- В контейнер может быть сложно прокинуть физические ресурсы: USB, GPU (если не настроить специально), сетевые порты на host и т.п.

**3. Потери в производительности**
- Имеет оверхед по сравнению с запуском "напрямую" (обычно минимальный, но бывают особенности при сборке больших проектов с файловыми операциями).

**4. Хранение артефактов**
- После завершения job’а всё, что не скопировал во внешний storage/volume — удаляется.
- Иногда неудобно настраивать кэширование между задачами (но это решается, если использовать volume mounts).

**5. Ограничения по безопасности**
- Если контейнер может исполнять Docker внутри докера (docker:dind), это может ослабить безопасность и дать job’у опасные права.

#### Kaniko executor

Неофициальный проект Google, не поддерживает RUN --mount, заморожен, изоляция через chroot и требует root в контейнере.
Его минусы в том, что вредоносный код может вылезти из-под chroot-а, завладеть root-ом на контейнере и пойти заражать хост и остальную инфру, менять переменные окружения CI-джобы, которая это всё крутит.

#### Buildah

Развивает RedHat, изоляция также через chroot(умеет при этом в рутлесс) или вложенную контейнеризацию

#### BuildKit

Часть Moby project, который родился из Docker, в нём много оптимизация по скорости сборки, умеет в рутлесс. Изоляция через qemu или вложенную контейнеризацию. Имеет максимальную совместимость с Docker и легко настраивается.
Деплоится как отдельный демон, что немного усложняет архитектуру CI, но зато изоляцию от, например, gitlab ci ns
