Docker состоит из трех проектов:
- [**docker-cli:**](https://github.com/docker/cli) утилита командной строки, с которой вы взаимодействуете с помощью команды `docker`.    
- [**containerd:**](https://containerd.io/) Linux Daemon, который управляет контейнерами и запускает их. Он загружает образы из репозитория, управляет хранилищем и сетью, а также контролирует работу контейнеров.
- [**runc:**](https://github.com/opencontainers/runc) низкоуровневая среда выполнения контейнеров, которая создает и запускает контейнеры.

На самом деле, когда вы запускаете контейнер с помощью `docker`, вы фактически запускаете его через Docker Daemon, containerd, а затем runc.

Kubernetes поддерживает только Container Runtime, которые работают с Container Runtime Interface (CRI), но Docker не поддерживает этот стандарт напрямую, поэтому Kubernetes включает компонент под названием dockershim, который необходим для работы с Docker.

---

**OCI (Open Container Initiative)** — это открытый стандарт, определяющий, как должны быть устроены образы контейнеров и сами контейнеры.

---

**CRI (Container Runtime Interface)** — это **стандарт API**, который определяет как Kubernetes взаимодействует с программой для запуска контейнеров (container runtime).

Как это работало раньше:
- В первых версиях Kubernetes использовался только Docker напрямую.
- Эта интеграция была не очень модульной и имела специфичные детали только для Docker.

Что придумали?
- Для унификации и поддержки альтернатив Docker, в Kubernetes с версии 1.5+ появился **стандартный интерфейс** — **CRI**.
- **CRI** — это набор RPC-команд, через которые Kubernetes (точнее, kubelet) общается с контейнерным рантаймом.

Для чего это важно?
- Позволяет **заменять и развивать контейнерные рантаймы** под различные задачи (без изменения Kubernetes).
- Например, если нужен легкий runtime — ставят CRI-O, если нужна совместимость с экосистемой Docker — containerd.

## 1. Историческая схема

Изначально Docker был монолитным демоном, который сам делал всё:
- работал с API,
- управлял образами,
- запускал контейнеры (через **libcontainer** и позже через **runc**).

Позже Docker начали “расщеплять” для лучшей модульности: появились **containerd**, **runc** и стандартизация на уровне образов и рантаймов (OCI).

---
## 2. Комплект основных терминов и ролей

### **dockerd**

- Это основной демон (процесс) Docker Engine — docker daemon.
- Отвечает за REST API, orchestration, работу с образами, volumes, сетью и всей "магией" наверху.
- Принимает команды пользователей (docker run, docker build и др.) и оркестраторов (например, Docker Swarm).

---
### **containerd**

- Это отдельный, более низкоуровневый демон — менеджер жизненного цикла контейнеров.
- Изначально был частью Docker, позже вынесен в отдельный проект (развивается как CNCF проект).
- Выполняет задачи:
    - управление контейнерами (создание, старт/стоп, удаление)
    - управление образами (pull, push, хранение)
    - снапшоты/слои файловой системы
- Docker использует **containerd** для реального управления контейнерами на низком уровне.

---
### **runc**

- Это ещё более низкоуровневая утилита (и библиотека).
- Конкретно отвечает только за запуск и остановку единичного контейнера на основе OCI спецификаций.
- Ход работы: containerd или dockerd вызывает runc run ... — runc "форкнет" процесс, запустит rootfs, namespaces, cgroups и т.п.
- runc — реальное "запускающее" звено, которое изолирует процесс и организует "контейнерность".

---  

## 3. Как всё вместе работает (на современном Linux-хосте)

### Когда ты набираешь docker run ...:

1. **dockerd** получает команду (через CLI утилиту или API).
2. dockerd:
    - проверяет, есть ли нужный образ (если нет — скачивает, сохраняет).
    - готовит конфиг контейнера.
3. dockerd обращается к **containerd** (через gRPC-API, внутренняя интеграция):
    - "создай мне контейнер из вот такого-то образа с такими-то параметрами".
4. **containerd**:
    - разбирает config
    - получает слои rootfs, снапшоты, потом говорит своему plugin’у “runtime”
5. containerd вызывает **runc**:
    - runc получает на вход bundle (набор файлов: rootfs + config.json по OCI)
    - запускает процесс внутри изолированного окружения (namespace'ы, cgroup'ы, seccomp, capabilities и др.).
    - runc завершается (как процесс) — контейнерный процесс “остается жить” под управлением containerd.
